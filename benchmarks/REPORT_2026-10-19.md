# Reference performance report — 2026-10-19

This report records the first reproducible DataPipette end-to-end baseline. It is a capacity observation for one test environment, not a universal production claim.

## Verdict

The safety architecture behaved correctly, but the accepted 5-million-row × 50-column / 20-active-client target was **not met** on this environment.

- The 5M × 50 refresh reached the default 30-minute source statement timeout and published no snapshot.
- A width-isolation run at 5M × 20 completed in 28 minutes 29 seconds and published a 130,559,605-byte Parquet snapshot.
- One interactive client completed every request with p95 latency of 1.17 seconds.
- At 5–20 clients, the installation-wide concurrency limit protected the node with explicit `503` admission responses, while admitted latency rose to 3.14–5.41 seconds p95.
- Two 250,000-row CSV exports completed successfully, but the single-concurrency worker executed them sequentially. Simultaneous heavy-job capacity remains unproven.

The immediate performance priority is the snapshot read/write path: stream or vectorize refresh conversion and avoid downloading and checksumming the complete S3 object for every interactive query.

## Synthetic source fixture

The deterministic PostgreSQL fixture contains 100,000 customers and exactly 5,000,000 events. The event relation has 50 selected benchmark columns plus its governed identifiers and contains no invalid generated identifiers.

| Operation | Duration |
| --- | ---: |
| Insert 5,000,000 events | 44.012 s |
| Primary key | 12.555 s |
| Three secondary indexes | 4.182 s, 2.692 s, 14.212 s |
| Analyze | 1.762 s |

The final event relation occupied 2,338 MiB: 2,056 MiB heap and 282 MiB indexes. The fixture is isolated in `datapipette_benchmark`; no business schema was modified.

## Refresh and publication

### Accepted-width run: 5M × 50

The first refresh attempt ran for 1,811.582 seconds and crossed the default 1,800-second statement timeout. It returned the governed `source_unavailable` failure and did not publish a snapshot. The automatically scheduled retry was cancelled through the public API after the first failure had already established the outcome. Safety limits were not raised to manufacture a successful result.

**Result: fail for the accepted baseline.** The workload cannot currently complete under the default policy on this node.

### Width-isolation run: 5M × 20

The Query Safety Advisor validated the query in 0.197 seconds without an override. It correctly reported a five-million-row sequential scan, high planner cost, and a large result. Preview returned 100 rows in 0.147 seconds.

| Metric | Result |
| --- | ---: |
| Rows published | 5,000,000 |
| Selected fields | 20 |
| Execution duration | 1,709.382 s (28m 29.382s) |
| Orchestration wall time | 1,710.918 s |
| Attempts | 1 |
| Parquet object | 130,559,605 bytes |
| Estimate / actual ratio | 1.0 |

**Result: pass as a diagnostic slice, not as acceptance of the 50-column target.**

## Interactive snapshot queries

Each virtual client held one persistent HTTP connection and rotated through point, categorical, date-and-numeric-range, and wide-page queries. Every level used a 15-second warm-up followed by a 120-second measured window. Latency percentiles include successful requests only; capacity responses are reported separately.

| Clients | Attempted | HTTP 200 | HTTP 503 | Success rate | Success req/s | p50 | p95 | p99 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 121 | 121 | 0 | 100.0% | 1.008 | 966 ms | 1,173 ms | 1,199 ms |
| 5 | 574 | 195 | 379 | 34.0% | 1.625 | 2,600 ms | 3,142 ms | 3,485 ms |
| 10 | 766 | 181 | 585 | 23.6% | 1.508 | 3,471 ms | 4,085 ms | 4,457 ms |
| 20 | 848 | 176 | 672 | 20.8% | 1.467 | 4,815 ms | 5,407 ms | 5,978 ms |

The `503` responses are intentional admission control rather than crashes or hidden timeouts. This proves bounded degradation, but it does not satisfy a product claim that 20 users can all execute continuously at once. The dominant current cost is that each S3-backed query materializes and verifies the complete 130.6 MB snapshot before DuckDB reads it.

## Background exports

Two CSV jobs were requested together. Each selected 12 fields and returned 250,000 rows.

| Job | Queue/start delay | Execution | Size | Result |
| --- | ---: | ---: | ---: | --- |
| 1 | 0.141 s | 8.810 s | 33,136,536 bytes | succeeded |
| 2 | 8.937 s | 8.469 s | 33,258,757 bytes | succeeded |

Both completed in 20.113 seconds of orchestration wall time. Because the worker concurrency was one, the second job waited for the first; this validates durable queueing and bounded execution, not two simultaneous heavy jobs.

## Conclusions and next measurements

What is already working:

- deterministic generation and reproducible API-only measurement;
- accurate planner estimates and explainable safety warnings;
- bounded refresh failure with no partial snapshot publication;
- cross-process admission control that rejects excess work explicitly;
- durable export queueing and successful large filtered exports;
- bounded observed application memory rather than node exhaustion.

What must improve before the target can be accepted:

1. Replace row-oriented refresh conversion with a streaming/vectorized Parquet path and re-run 5M × 50 under the unchanged policy.
2. Introduce a verified local object cache or direct/ranged S3 reads so interactive queries do not transfer the full snapshot per request.
3. Re-run interactive tests and define an explicit latency/SLO target in addition to concurrency.
4. Run the heavy-job scenario with worker concurrency two and capture peak CPU, memory, I/O, and overlap.
5. Repeat the complete suite after each optimization and retain the raw JSON for comparison.
