# Dashboard capacity — 2026-10-30

How many people can use dashboards at the same time on a small single-server installation, measured with the `dashboard` workload described in [README.md](README.md#4-simulate-dashboard-viewers).

## Setup

| | Test server | Development machine |
| --- | --- | --- |
| Hardware | 4 vCPU, 7.7 GB RAM, Ubuntu 26.04 | 8 CPU, 4 GB for Docker, macOS |
| Topology | production overlay (Caddy TLS → Nginx → API) | evaluation `compose.yaml` |
| Dashboard | 6 charts from 3 datasets (up to 100,000 rows), no filters | 7 charts from 2 datasets (48,000 and 1,200 rows), 3 filters |
| Load generator | container on the same host, through the TLS gateway | same machine, plain HTTP |
| Policy | default: 4 interactive queries at once | default: 4 interactive queries at once |

Each virtual viewer:

- loads the layout and every chart over at most six connections;
- picks filters in half of the views (when the dashboard has filters);
- retries a `503` twice, one second apart, like the frontend;
- waits about three seconds before the next view.

A view counts only when every chart loaded. Runs lasted 60 s after a 15 s warm-up. Raw results are in `results/dashboard-*.json`.

On the test server the load generator shared the four CPUs with DataPipette, so its numbers are conservative.

## Results

### Test server, one API process (the default before this change)

| Viewers | Views/s | Fully loaded | Median view | 95th percentile |
| --- | --- | --- | --- | --- |
| 1 | 0.30 | 100% | 0.46 s | 0.52 s |
| 5 | 1.27 | 100% | 0.75 s | 1.49 s |
| 10 | 2.03 | 100% | 2.25 s | 3.22 s |
| 20 | 2.23 | 100% | 6.91 s | 8.13 s |
| 40 | 2.30 | 70% | 20.3 s | 33.2 s |

Throughput stopped growing at about 2.2 views per second, while the API process used about 1.5 of the 4 CPUs. The datasets are tiny, so the time goes to per-request work in one Python process: authentication, metadata reads, admission, DuckDB setup, and audit. At 40 viewers nine requests failed with HTTP 500, because PostgreSQL ran out of connections (see below).

### Test server, three API processes

| Viewers | Views/s | Fully loaded | Median view | 95th percentile |
| --- | --- | --- | --- | --- |
| 10 | 2.68 | 100% | 0.56 s | 1.78 s |
| 20 | 3.88 | 100% | 2.04 s | 4.79 s |

Three processes cut the median view at 10 viewers fourfold and raised throughput by 75% at 20 viewers. Some requests now reach the four-query admission limit and are retried.

### Development machine, one API process

| Viewers | Views/s | Fully loaded | Median view | 95th percentile |
| --- | --- | --- | --- | --- |
| 1 | 0.32 | 100% | 0.19 s | 1.47 s |
| 5 | 1.53 | 100% | 0.21 s | 1.23 s |
| 10 | 3.03 | 100% | 0.21 s | 0.59 s |
| 20 | 5.75 | 100% | 0.33 s | 1.50 s |

With seven charts, a single viewer already exceeds the four admission slots, so some charts are rejected and wait a second for the retry. That delay is the source of the 95th percentiles above one second.

## What the numbers mean

A viewer in these runs opens or refilters a dashboard every three seconds without pause, far more often than a person reading charts. People typically look at a view for 30 seconds or more. Allowing for the extra headroom of the three-process configuration:

- **4 CPU / 8 GB with three API processes:** about **80 people actively working at the same time**, with dashboards opening in about half a second (2.7 views/s at a 95th percentile under 2 s, one view per person every 30 s). Short bursts of 20 people clicking constantly still load completely, in about 2 s.
- **The same server with one API process:** about **40 people**. Beyond 10 constant clickers, views take several seconds.

These figures hold for small and medium datasets. Charts over multi-million-row snapshots spend real time in DuckDB, so measure with your own dashboards before relying on them.

## Changes made because of this measurement

- **`DATAPIPETTE_API_WORKERS`** sets the number of API processes. `new-env.sh` chooses one process per CPU, minus one, up to four. Admission stays installation-wide across processes (ADR-0041).
- **No more HTTP 500 under overload.** Every admission attempt opened its own PostgreSQL session. A burst of chart requests exhausted `max_connections`, and ordinary requests then failed. Each API process now refuses admission attempts beyond the limit plus four without touching the database. Connection failures of metadata PostgreSQL return `503 service_temporarily_unavailable` with `Retry-After`. Repeating the overload (60 viewers, 0.5 s think time) produced only `200` and `503` responses, with 12 database sessions in use.

## Follow-ups

- Let the frontend send at most as many chart queries per page as the admission limit, so a single viewer never waits for a retry.
- Profile per-request overhead in the API (authentication and metadata reads), the largest cost for small datasets.
- Repeat the measurement with the load generator on a separate machine and with a multi-million-row dashboard.
